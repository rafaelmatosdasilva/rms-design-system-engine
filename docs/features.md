# Everything it does

The [README](../README.md) gives the overview. This page shows how to use each part, what the style guide holds, how prototypes and the checks work, in plain words. For developers, every option and how each check works is in [the technical details](details.md).

## Use it

The easiest way is to ask in Claude Code, in your own words, after `/rms-design-system-engine`. The terminal command does the same.

| You want to | Type in Claude Code | Or in the terminal |
|---|---|---|
| Check the whole design system | `/rms-design-system-engine check everything` | `rms-design-system-engine` |
| Check one component | `/rms-design-system-engine check the button` | `rms-design-system-engine --component button` |
| Check against Figma only, without accessibility | `/rms-design-system-engine check the button against Figma, without accessibility` | `rms-design-system-engine --only parity` |
| Check accessibility only | `/rms-design-system-engine check the accessibility of the button` | `rms-design-system-engine --only accessibility` |
| Run one check (a gate) | `/rms-design-system-engine run only the token values check` | `rms-design-system-engine --only 3` |
| Ask what the design system has | `/rms-design-system-engine which props does the badge take?` | `rms-design-system-engine --query badge` |

You can mix them. `rms-design-system-engine --component button --only accessibility` checks only the accessibility of the button.

**Every difference in one list.** Each full check writes `.design-system-engine-out/differences.md`: every difference between Figma and the code, grouped by component, with what is new since the last check. It is written whether or not you have a style guide, and the summary of every check says where it is. It also names each check that did not run, so a gap is never mistaken for a pass.

### The style guide

`rms-design-system-engine --styleguide` builds a living style guide of what Figma and the code agree on, in `.design-system-engine-out/styleguide/index.html`. Add `--component modal` and it audits that component first (every check against Figma and the accessibility check in a browser), then builds the page and prints the address of the component on it, so its Accessibility and Parity are as of now. **[See an example](https://rafaelmatosdasilva.github.io/rms-ds-figma-plugins/)**: the RMS Design System's style guide, built by this engine and published by that design system, so it shows what the engine makes today. Every project fills the same template, the one in the engine (`templates/styleguide.template.html`), with its own data, so an improvement made there reaches every design system on its next run.

- **Its look is your system's.** The template is only the layout: every colour, text style, radius, space and the icon size on the page is one of your tokens, the page's text is your own body rule and inherits your page font with its fallbacks (the names of props, variables and classes too: one font on the page, never the browser's monospace), and every switch, text field, button, link and card on it is your own segmented control, text field, button and card. The page never draws a control of its own. When your system lacks one, the page uses its nearest stand-in from your system (no segmented control: your tabs, then your radio group, then your buttons side by side; no text field: your search field), else a plain control drawn with your tokens, and says so on the overview and in the To do list, for your team to decide whether the system needs it. The engine checks the built page and fails it when anything on it is not from your system (a button or link it styles itself, a font of its own), when its own text is below 4.5:1 on its own background in any colour mode, or when it breaks an accessibility rule it checks you by.
- **To do.** Everything open in the system, by component, one card table each: what differs from Figma, what Figma has that the code does not build yet, a prop or variable only one side has, and for accessibility what the audit and the code found and what is still to check (a role not stated in Figma). Each row is numbered and says its area (Parity or Accessibility), exactly what to do, who acts (You in Figma, a change you make in the Figma file, a colour that fails contrast included, since Figma's colours are yours; Claude in the code, tell Claude its number; You decide, when Figma and the code each have a case; You check by hand, what only a person can judge), said once above the tables, whose columns line up from one component to the next and whether it is to fix or to check, the system's own items first and a count of each at the top, so you can answer with the numbers (do 3 and 7). The numbers run in order from the top of the page down (the system first, then each component by name, in each what is to fix before what is to check), and a component's own areas name the same numbers. With the To do page open, every component is tried in the browser in the background, as its own Accessibility area tries it, and the list grows as each one is done; its count shows once all are, and what was found is kept in that browser for that build of the page, so the next visit is complete at once. Each component's numbers match what its own areas show (a contrast the audit found per variant is one row each here and one criterion there).
- **One view at a time.** The overview has a card for each foundation and component, each with a thumbnail (a few of the real tokens, or the component itself drawn small) and its name; opening one shows only that foundation or component, at its own address you can share (`#c-badge`). A search covers everything on the page (components with their descriptions, annotations and props, every token by its Figma name and variable, type styles, icons, to-dos and sections): while you type, only its results show, just below the field, and choosing one opens it and marks it on the page (Enter opens the first, Escape clears), and every button on it says what it does in words, never an icon alone: on a phone, Menu at the top opens the navigation as a panel and Close menu shuts it; on a wide screen the menu is always there. The thumbnails are drawn in the browser from your own code each time the page opens, so they never need regenerating. The engine opens the page with `?all`, which draws every view at once and no thumbnails, for its own checks; it does so with your published page too, so a shrunken thumbnail is never measured as the component.
- **One name, one look, on every page.** Each page's title is its name in the menu, in the menu's own case (overview, to do, colors), 8px under its tag, in your system's own heading style when it has one clearly larger than its body text (at least 20px and 1.6 times it), else at 3.125 times its largest text style, so the guide has its own hierarchy whatever sizes the system has (`"title-scale": "2"` in `styleguide.chrome` changes the scale); the overview has no descriptions, only its groups and cards; the menu's groups (Start here, Foundations, Components) sit 24px apart, its links in your system's l text size, 8px apart, the page shown on your system's page background; each page's tag is the name of the menu group it sits under, so renaming a group renames the tags. Every bar that stays at the top as a page scrolls (a component's areas, a page's title, a foundation's size switch, kept under its title) is drawn alike, with a line under the lowest once it is stuck.
- **Foundations.** Under their own label in the menu. What the whole system shares: colours (the primitive ramp first, then the semantic roles, each group a list in one card with its name as the card's head, each colour with its sample (every sample on these pages the same height, so a space reads as its width), its Figma name, its variable and the value it is drawn with, and a Light and Dark switch above that changes only the samples and their values), typography (Figma's text styles in Figma's order, each beside a token table, as a component has: its family, size, weight, line height, letter spacing and case, each named by the Figma variable the style binds, then the code's variable and the value), spacing (one card per family, gap or padding, its name as the card's head, smallest first, each space with its sample, names and value), radii (listed the same way) and icons (grouped by their own size, with their stroke widths). Anything named after a component (its colours, its sizes), or that only a component's tokens point at (window chrome colours an action bar uses), is shown in that component instead; a component Figma has without props (a divider line) has its own view. Each is the CSS variable itself, shown only when the token check finds it equal to Figma in every mode. A size that changes with a mode shows the value of the mode picked on the section's size switch, as a component does, so you see the spaces and text styles change. Icons are shown at the size Figma gives them and under their Figma names, one card per size with the size as its head, on a grid of equal cells so they line up across and down; their stroke widths are listed as the spacing is.
- **Components.** Each one drawn from your own markup (the contract's probe, an instance in your pages, or what its React source returns) with your own CSS: the instance that holds every part its props show or hide, so turning an icon or a label on or off shows it or hides it. A part no instance in your products has is drawn from your own CSS for it (an icon from your icon sheet, a text part with its own name, such as Description), and a Figma prop your code does not build yet is listed as such, never drawn with Figma's look. Its controls are the props both sides have, labelled with Figma's names and in the order of Figma's panel (variants first, then the rest as Figma lists them, a prop not built yet in its place, and a text right after the boolean that shows it, Show Text before Text Content); every text prop writes into the part whose own words it is, and a part your CSS draws as a shape (a priority dot) stays empty and comes before the words; an option applies what your contract's propertyMap says it adds. In a plain HTML and CSS system the controls are the Figma props your code realizes (the contract's propertyMap, `htmlRealizations`, a modifier class). Each one is centred in the playground at every width (one wider than it scrolls from its start), and one that lives inside another (one segment of a segmented control) is drawn once, inside its parent. Every state can be chosen, hover, focus and pressed too (the system's own rules for them, applied without a mouse), a state set on a part (a checkbox's input ticked) is set there, and choosing the option already set changes nothing. Using the component in the playground sets its props too: tick a checkbox, pick a radio, flip a switch or type in a field and its controls follow; editing a label changes only its words, so whatever else is set stays. A Figma option your code does not build is offered but marked so, and an option your contract maps to a product's own markup is read from the component's own CSS instead (Selected from its `:checked` rule). A component shown in an overlay opens over the whole window, as in a product. Its documentation at the bottom is Figma's description and annotations, its slots (how Figma lets each be filled: any content or only its preferred components, how many, empty at first), then the code's own note; when Figma was last read for it and every commit that changed its code are in its Changelog; on a phone it reads in one column, each name above its text. What still differs from Figma is marked on its Parity area with your system's alert icon and listed there, in two columns of tables, in plain English, each with who acts (you in Figma, or the code) and exactly what to do. Each one works as in your products: a selection moves when you click it, your system's own scripts run (`systemScripts` in `ds-config.json`), a component shown in an overlay opens in it with its own animation from a button, and an entry or exit animation can be replayed, its button at the bottom left of the playground, on the same bar as the colour mode. Your system's modes are switched inside the playground, named as your Figma collections are (Styling, Sizing): the colour mode at its top left, the other at its bottom right, with no label over them, apart from the component's own props. Below it, the tokens behind what is drawn now (each visible part, read again on every prop change; a text a prop hides takes its text style and colour out with it) with its code on their right, the code as tall as what it holds and scrolling inside only past the tokens' height. Every token the component has is listed in Parity, each variable's name opening its value per mode and what else uses it. A component your system defines by an id (a tooltip, `#tt`) is drawn with that id's own rules and shown as it is in use, in place in the playground. Documentation, Accessibility and Changelog are grouped in the same tables, and every box on the page has your card's border, corners and shadow.
- **A component's page, in areas.** Above them, its name and how a product imports it (`import { Chip } from '@/components/Chip'`, with your button to copy it and one to download its file; in a system of CSS classes, the stylesheet that holds its rule, by the name your package's exports give it, `@import '@acme/ds/theme.css';`, and the functions of your system's own script that build or drive it, `showToast(msg, opts)` from `@acme/ds/ui-shared.js`, or their import when the script is a module, each read from your code for that component). Then one area at a time, switched with your own tabs that stay at the top as the page scrolls (with none in your system, the page's own: the area names in a row, a line under the chosen one and under the whole row, in your colours, text styles and spacing, with no note about it, in your largest text style, the words twice as far from the line as they sit from the top) (on a phone it scrolls sideways in one row, the area you chose brought into view, and the playground keeps room for the component below its mode switches), with the component's name beside it once its heading has scrolled away (a foundation's title stays at the top too), a component always opening on its Playground, each area under its own title with its content 16 pixels below: **Playground** (the component, its controls and Width, the tokens behind what is drawn and its code), **Specs** (its parts, paddings and gaps), **Variants** (every option of each variant prop and both sides of each on/off prop, one per row, in the page's colour mode, with Try it to set it in the Playground; every component with a variant or an on/off prop has it, one with only text, slots or swaps does not), **Documentation** (its usage, its API, Figma's and the code's own words), **Accessibility**, **Parity**, **Built with** (the system's components it is made of, each the overview's card with its own preview, linked to its page), **Used in** (a product that draws its own version instead, found by Gate [10], is there too, said so) and **Changelog** (Figma first: when it was last read, then every read that changed what Figma says of it, with what changed, a property added or renamed, an option, a variable's value in a mode; then every commit that changed its code, followed through its own rules so a change inside a rule counts, by the release it shipped in, each release linked, each commit linked with its pull request and a short note of what it changed in its rules, padding --padding-s → --padding-m). Its version is the release its last change shipped in. The Playground is one card: the stage fills its left side to the edges, the controls are on its right. A table's own head is as tall as the card's head above it. In the Playground, every Figma slot is shown as the area it takes (Inspect on it says only that it is a place for content and the spacing Figma gives it, its padding and gap, checked against the code's like every other part's): dashed, named Slot inside, in place of its placeholder (in the part that holds it, `.modal-slot`, or in place of the content a card or a status bar holds, at least the size a slot needs to be read, so the component grows around it and its other parts still show), while the HTML shown stays your markup; a slot only Figma has is listed in Parity. Then how ready it is (stable, beta or deprecated, only when your team said so: a `Status: beta` line in its Figma description or annotations, `@deprecated` or `@status beta` in its code, or `status` in `contract.authored.json`) and how much of its file your tests cover (from the coverage summary your tests write, `coverage/coverage-summary.json` or `styleguide.coverage`); its status is on its overview card too. Beside it, its version (the release its last change shipped in) and when it last changed, date and time; each overview card is its picture and, below it on your table heads' background, its name (a Used in card adds a line under the name on the same background; the card's corners round the picture's top, its bottom stays square), and the Accessibility and Parity areas carry your alert icon before their label when something needs work (on Accessibility, anything its table has to fix or to check) (on Parity, anything its table marks: a row that differs, one only in Figma or only in code, a prop not built). Parity's table keeps its head in view under the areas as its rows scroll by, and a Figma slot or component swap counts as built when your markup takes content (with code props, a slot is `children`). Each overview group says what it holds (`styleguide.groups` words it your way). Its version, when it last changed and its import share one line, wrapping when the room runs out. At its top right, its links, said as where they take you (See in Figma, See in code) with your system's icon for a link that opens elsewhere: its node in Figma, its code (its own file, or the line of its rule in your stylesheet) and your team's pages (`styleguide.componentDocs: "https://wiki/…/{name}"`, or `links` in `contract.authored.json`). The overview has Send feedback (`styleguide.feedback`, else a new issue in your tracker, `styleguide.issues`, or your repository's own on GitHub or GitLab). The overview links the Figma file, the repository and `styleguide.links`. The import path is the file's package and path, else `@/` and its path under `src/`; `styleguide.importFrom` (`"~/ui/{path}"`) writes it your way. Each area has its own link to send someone to (`#c-chip/accessibility`, `#c-chip/documentation`), kept in the address as you switch areas.
- **Usage, the same on every component.** When to use, When not to use, Common mistakes and Limitations, each read from what your team already writes: a line of the component's Figma description or annotations that starts with the section's name (`When not to use: for navigation`, or the name on its own line with the text below), the code's own note, or `contract.authored.json` (`components.<name>.guidance`). A section nobody has written says so, except Common mistakes, which then shows what the last audit found your products doing with the component (a rule laid over it, a look-alike built by hand), and the overview counts how many components have each one.
- **Width.** Width shows the component at each width your Figma file gives its breakpoint modes (a viewport width variable, `viewport/min-width`: Phone 350, Desktop 1680), else at 375, 768 and 1280 pixels, without resizing your browser, with your own stylesheets, so your media queries apply, and your scripts run in it, so it works there too; Fit brings back the live preview. The address follows what you set in the Playground (`#c-chip?Size=L&width=phone`), so a link opens that exact variant; the other areas' addresses carry only the area. The stage is never narrower than a phone screen and its margins: with less room the controls go below it, and a component wider than the stage scrolls inside it, never over the controls.
- **Figma beside the code.** In the Playground, the Figma button shows Figma's image of the variant you set beside the component as your code draws it, or over it with a slider that reveals more or less of Figma, a small one drawn larger. The images come from your references folder (`.design-system-engine-refs/components/<name>/Size=L, State=Default.png`, each variant named as Figma names it) or, with `FIGMA_TOKEN` in `.env`, straight from Figma, every variant at once. A variant with no image says so.
- **Do and Don't.** Pictures of the right and wrong use, each named for what it shows, in your references folder (`.design-system-engine-refs/components/button/do/Labels that say what happens.png`, and `dont/`), or Figma frames your contract names (`examples` in `contract.authored.json`, read with `FIGMA_TOKEN`), shown in pairs under Usage.
- **What's new.** Every release and what it changed, one row per change with the components it touched, from your code's history.
- **One way of writing names.** Every property and option name in your Figma file is read for how it is written (Show Icon, show-icon, showIcon), and the way most of the system writes them wins; each name written otherwise is listed in the audit's list of differences, on its component's Parity and in the To do list, with its rename for the Figma file, and a misspelt option (sucess) is named as the word it meant.
- **A token's panel.** Click any token's name on the page and a panel opens right there: its Figma name, its value in each mode of each collection that changes it (Light and Dark, Desktop and Phone, the one drawn where you clicked marked, else that it is the same in every mode), the components that use it, in their own rules or through another token (`--button-background` naming `--neutral-100`), each linked, and a button to copy it, so you know what a change to it touches without leaving the page. Search finds props too.
- **Inspect.** In the Playground's top bar: the Width goes back to Fit, so the component sits in the middle of the stage, and the Playground turns into the component's anatomy, as you set it, at the size the Playground draws it (never scaled down; one wider than the stage scrolls) and redrawn with every change, each part, padding and gap outlined (never filled with a colour, so nothing reads as a token's colour). Click one and the bar below says in one line what it is and its value (`chip padding left · --padding-s · 8px`, an icon's size and colour), the rest dimmed around it. Click inside it to reach what is nested there, one level at a time (`Actions › buttonSecondary › text`), and click it again to go back up; click outside the component to let go. Switch Light, Dark, Desktop or Phone while inspecting and the drawing follows; pick a Width and it is drawn at that width instead of the Playground's. Done inspecting brings the live component back and removes the anatomy. The sizing mode sits in the bar above the component and the colour mode in the bar below it, so the stage stays apart from what changes it.
- **Parity.** One table of everything the component has, whatever the Playground shows: every prop, every variable and every value compared, each with its type, Figma's name and value beside the code's, a status you read at a glance (a sign in the system's colours: the same, differs, only in Figma, only in code) and the date and time it last held. Filter it by props, variables or values. What differs sits below it, a row each naming the component or part, who acts and what to do. Both are in the same card table as the Playground's. On a phone every table of several columns reads as a block per row, each value under the name of its column, so nothing is squeezed, cut or drawn over; a filter or a control with many options scrolls sideways, and the page fits 320 pixels.
- **Used in.** A card for each of your products that uses it, with the product's own picture (`docs/preview.png` or a screenshot in its folder, or `styleguide.plugins[].image`), its name, linked to it, and how many times the component appears in its code. A product with no picture of its own is pictured as its page opens, with each place the component sits on it marked.
- **Code.** Under each component, the code for exactly what the playground shows, with your button to copy it. In a framework system it is the component as a product writes it (`<Chip size="l" />` in React, Svelte or a custom element, `:on="false"` in Vue), with each value as your code spells it, a default left out, and every prop your code requires written even when the playground does not set it. In an HTML and CSS system it is the HTML drawn, with only the classes your CSS styles.
- **API.** The props your component's file declares, each one it requires marked with a * (and read as required by a screen reader), with its values and default; the events it sends (Vue's emits, Svelte's dispatch, React's onChange-style callbacks) and its slots, with the file they were read from. Required only ever means what the code says: a prop with a default is not required, and a prop nothing marks is never guessed. An HTML and CSS system has no API to read, so the section is left out.
- **Accessibility.** One table, by WCAG 2.1 criterion at level A and AA, of only what applies to the component: what was found (each finding or duty naming the component, its variant or the part it is about), where it is read from (a Figma annotation, your contract, your code, the style guide in the browser, the last audit, a person), and its status, in the same card table as the Playground's; what a criterion means opens from its name on a click or when the pointer rests on it (To fix, To check, Done) with a count of each above it and when the audit last ran. What belongs to the page that uses the component, video and sound it does not play, and what asks of controls or fields on a component with none, are left out. To fix comes first. Every variant is tried in the browser (the Tab stops, names, focus, text contrast in every colour mode, images, groups, reading order, control edges, hover and focus content, motion, links, label in name, valid ARIA, status messages, and what it does when used), the audit adds real key presses, zoom, text spacing and a keyboard trap, and your code is read for single-key shortcuts, short timers, gestures and device motion. Colours are read once a mode has settled, never halfway through the component's own transition, in the page and in the audit. A criterion that passes says so and where it was tried (Passes in all 8 variants); one a person still checks says no problem was found there, then what the person looks at. What only a person can judge says what to look at. Below it, a table lists what no check reads: each Figma annotation on it or its layers that no check reads, with how to write it so one does, and the section of your guidelines from Notion or GitLab named after it (read by the agents).
- **Modes.** A switch for each of your mode collections on each component (and each foundation section), and the colour mode for the whole page too; a component's own switch is independent of the page's, so a component in Light on a Dark page looks exactly as it does in Light. The modes are listed in Figma's own order. By default the page switch is on Auto, which names the mode it found, and the page and every component use your computer's and browser's own settings (Dark when it is set to dark, Phone sizes in a narrow window) and follow them when they change, until you pick a mode; a change on the page's switch applies to every component. A breakpoint mode your theme draws in a media query (a phone size, say) can be switched on any screen, and the switch lists what the mode changes (padding/xs 4px → 8px). A mode your code has no CSS for yet is shown as such, never drawn with Figma's values.
- **Last update.** Each component shows when its code last changed (the latest commit on its CSS rules and its contract and config entries, or that a change is not committed yet) and when Figma was last read for it.
- **In use.** The approved pictures of your Figma frames (the ones the frame check compares against), when there are any.
- **Not agreed yet.** A prop only one side has, another default, a token that differs or a component not built yet is left out and counted in one line at the top, so you decide each one before it appears.

A project can still use a template of its own (`ds-config.json` → `styleguide.template`).

### Bring Figma in line with the code

When the code already states something Figma does not, the engine can write it into Figma for you. Today that is each component's role: a component built as a real `<button>` or `<input type="checkbox">` whose Figma component says nothing about it gets the note `Role: button`, the note every later check reads.

| You want to | Type in Claude Code | Or in the terminal |
|---|---|---|
| Update Figma to match the code | `/rms-design-system-engine update Figma to match the code` | `rms-design-system-engine --figma-edits` |
| Send the prototypes' gaps to Figma as a to do list | `/rms-design-system-engine send the gaps to Figma` | `rms-design-system-engine --figma-edits` |
| List in Figma the accessibility annotations no check reads, with the wording one reads | `/rms-design-system-engine update Figma to match the code` | `rms-design-system-engine --figma-edits` |
| Read the category of each Figma annotation (Accessibility is a requirement; Intent, Implementation, Content and Authoring are design intent, never a To do) | `/rms-design-system-engine refresh the Figma data` | `rms-design-system-engine --annotation-categories` |

- **You see the list first.** Each change names the component, what it adds and why (what the code renders, in how many places). Nothing changes until you say yes.
- **The engine writes the change, not the AI.** It writes the script, Claude runs it through the Figma MCP, and the project hooks refuse any other write to Figma.
- **Only what the code already proves.** A component whose role differs between Figma and code is listed for you to decide. Descriptions, missing components and layouts are never written; they stay on the hand-back list for your design team.

### Start from Figma only

Open an empty project, set it up with your Figma link, and ask for what to build. With no code yet, the engine starts in build mode: what Figma has and the code does not is listed as to build, in order, never as a failure.

| You want to | Type in Claude Code |
|---|---|
| Build the tokens | `/rms-design-system-engine build the tokens from Figma` |
| Build a component | `/rms-design-system-engine build the button from Figma` |
| Build a screen from the components | `/rms-design-system-engine build the settings screen from Figma with our components` |
| See what is left to build | `/rms-design-system-engine what is left to build?` |

Claude writes the code; the engine gives it Figma's exact names and values first and checks every piece after.

Measured on a small design system in Figma (tokens, four components and a screen), Claude with the Figma MCP alone built 8 of 18 pieces right with Opus, 16 of 30 with Sonnet and 4 of 18 with Haiku. With the engine all three built all of them. The [case study](../CASE-STUDY.md) gathers every measurement in a few pages; the full log is in [test/skill-evals/RESULTS.md](../test/skill-evals/RESULTS.md).

## Prototype with your design system

A prototype here is made only of your design system's own components, with their own options. Nothing is invented and nothing in the system changes. When a screen needs something the system does not have, the prototype shows a labelled box and you get a list of what the system would need, for your design team to decide.

Measured on eleven prototype requests, Claude alone made 17 of 33 right with Opus and 3 of 33 with Haiku; with the skill, 33 of 33 and 32 of 33 ([case study](../CASE-STUDY.md)).

| You want to | Type in Claude Code | Or in the terminal |
|---|---|---|
| Make a prototype | `/rms-design-system-engine prototype a notification settings page with our components` | `rms-design-system-engine --prototype prototypes/settings.json` |
| See what a prototype may use | `/rms-design-system-engine what can a prototype use?` | `rms-design-system-engine --prototype --catalog` |
| Start from the screens you designed in Figma | `/rms-design-system-engine make prototypes from our Figma screens` | `rms-design-system-engine --prototype --from-screens <screen capture>` |
| Check that the product's pages match | `/rms-design-system-engine are our prototype pages consistent?` | `rms-design-system-engine --prototype --consistency` |

- **What a prototype is.** A short file listing which components go where, with which options (`prototypes/<name>.json`). The engine checks it first; one that uses a component or an option the system lacks is not drawn, and each line says why.
- **What you see.** One page with your real components and tokens, in light and dark, under `.design-system-engine-out/prototypes/`.
- **Drawn as your system draws it, even from your products' pages.** Where your components' markup comes from your products' own pages, a prototype takes only what is the system's: a segment is drawn inside its segmented control, a panel's head and main take what the prototype puts in them and nothing the product had there, a product's own layout (its panel's width) and its words (a control named "Browse") stay in the product, and each option lands on its part (a switch turned off, a field's value, a field disabled for a screen reader too). What your system makes fill its container fills it, as Figma's fill container does, and a prototype can say so of any part.
- **Everything the engine knows goes into it.** Before Claude writes a prototype it is shown what was read (Figma, the code, your recorded decisions, your guidelines from Notion, GitLab or the project, each with its age) and, for what you asked, the guidelines that apply, the components your words point to and the screen to start from. Each component comes with what it is for: Figma descriptions and annotations, option notes, code notes, when to use it and when not, common mistakes, limitations, its Do and Don't, and what instead, without the notes written for whoever builds it (node ids, CSS). The screens your designers made for each product are listed with the components each one uses, and a request that names a product gets its screen in view. A use your Do and Don't or a common mistake describes is caught like one your guidelines rule out. A retired component is never used, a rule like "one button per screen" in your guidelines is held by the check, a component your documentation says never to use for something is not used for it, and after drawing each component is listed beside what the prototype uses it for, so a use your documentation rules out stands out.
- **Pages that match.** A new page is compared with the product's other pages: page padding, space between sections, screen width, heading and body text styles, where the actions sit, what each action is called and which component it is (never Save on one page and Submit on another), and the answer given to each need the system lacks. Even with no patterns or templates in your system, the first page made sets the rule for the next, and the pages of a flow are held to each other, with a way back on every page after the first. Each difference is listed with the pages it differs from. A screen your designers made counts on its own; your team can also write its decisions down in `prototypes/conventions.json`.
- **Seen in the browser.** The drawn page is opened in Chrome and measured against the screen your designers made: the same spacing, each part in its place, each component at its Figma size. A screen read from Figma keeps its colour mode, its window size, its own words and its components' states. A picture of the page is saved for you and for Claude to look at, with the Figma image of the screen you also get how many pixels differ, and the page goes through the accessibility check too.
- **Every state.** A page comes with its other states, such as empty, error and loading, each switchable on the page. A page with a list must have an empty state, one that takes input an error state, and any state your guidelines or your request name, or Claude has to say why not.
- **Every screen size, with longer words.** Each state is tried at every screen width, from phone to desktop, and at the page's own width when it has one (a plugin's window), with the words as written and 40% longer, as a translation makes them. What runs off the screen, a cut or spilling text, a button label on two lines and a target too small to tap on a phone are listed, and a picture is saved for each width and each state.
- **Click-through flows.** Pages link to each other, so you can click through a sign-up or a checkout. The links are checked against the flows your guidelines describe: a step with no page, or two steps that do not lead to each other, is listed.
- **A design review before you see it.** Each page is reviewed in the browser and scored out of 10: parts that line up, one spacing rhythm, one main action, a heading that leads, lines short enough to read. Claude fixes what scores low, and tells you what it kept.
- **It works.** The page runs your system's own scripts: a selection moves (and what follows it, like a sliding pill), a toggle turns on and off on its own, a field takes typing, a tooltip shows the words the prototype gives it, and a button can open a dialog or a menu from the prototype, drawn as your system draws it, keeping the focus inside a dialog and closed with Escape. Each one is tried in Chrome, and what does not work is listed. Each control the prototype draws is named for a screen reader; one that is not is listed for Claude to name, apart from what your system's components do themselves, which is the audit's.
- **Layout.** Where your system has no layout components, the engine lends neutral ones (a page, a stack, a row, columns) that only take your spacing tokens and your text styles, and puts layout components on the list.
- **Your screens as starting points.** Each screen designed in Figma becomes a prototype with the same arrangement and your components in place. The capture is read from Figma and never changes it. What a screen uses that the system does not own (a local component, a container with its own look, a typed number) goes on the list too.
- **The list.** Every prototype's gaps are kept in `.design-system-engine-out/prototypes/gaps.json`, the most needed first. Ask to send them to Figma and they become the design team's to do list there, on a page of its own, one card per need, written only after you say yes.

You get a short summary back: what passes, what is different, and how to fix each thing. Nothing is changed until you ask for it.

## The checks

Each check is called a gate. To run just one, use its number or its name, for example `--only 3` or `--only "token values"`.

| # | Gate | What it looks at |
|---|---|---|
| 1 | Data is up to date | You are comparing with today's Figma, not an old copy |
| 2 | Figma frame unchanged | The design still looks like the version you approved |
| 3 | Token values match Figma | Colours, sizes and fonts, in every mode (light and dark) |
| 4 | Tokens used in screens exist | Nothing a screen uses is missing from the code |
| 5 | Every mode is covered | Things that should change between light and dark really do |
| 6 | Exception lists are valid | Your "ignore this" notes still point at real things |
| 7 | No invented CSS variables | Every variable in the code comes from a Figma token, and carries that token's Figma name (a variable called by another name is listed; `figmaNames: "strict"` fails it) |
| 8 | Docs tell the truth | Your docs mention only things that exist |
| 9 | No invented text casing | No forced UPPERCASE the design did not ask for |
| 10 | No hand-built DS components | Screens use the real component, not a hand-made copy, and no product draws its own version of something the system has (a loading state and spinner of its own beside the system's loader), found by what it draws (the same looping animation as a component's part) or by its name (a class of its own that starts with a component's name); each is in the To do list and in that component's Used in |
| 11 | Clean CSS | Nothing unused, nothing that contradicts Figma |
| 12 | Nested components keep their styles | One component's look does not leak into another |
| 13 | Structure matches | Heights, spacing and corners, each measured in a browser. A height your code leaves to its content is compared by what Figma says: a fixed Figma height against the height drawn, a hugging row by its drawn height too, a hugging stack by how its height is set, and a component Figma sets to fill its container agrees when the code leaves its height to the page. Padding, corners and gaps Figma sets with no variable are compared too, every side and corner at each breakpoint, and a line height or letter spacing Figma gives in % is worked out from Figma's font size, never the code's. A text part with its own colour is compared in every colour mode, and a mode Figma has no value for is said, not skipped. Min and max width, how auto layout lines children up, wrap and a dashed stroke are compared too, and so are the first text's decoration, italic and alignment |
| 14 | All states are built | Hover, disabled, selected and the rest |
| 15 | Component props match Figma | The same names, defaults and choices, and one way of writing names across the system |
| 16 | Sub-components match Figma | The parts inside a component are the right ones |
| 17 | Templates compose the right components | Each page is built from what Figma shows |
| 18 | Markup matches | Classes, icons and every control the design shows |
| 19 | Required pieces are in place | Icon slots, component slots and form fields |
| 20 | Icons match Figma | From the shared set, drawn the same way |
| 21 | Transitions match | Durations and easing |
| 22 | Motion matches | When your design defines it |
| 23 | Shadows match | When your design defines them |
| 24 | Renders correctly in a browser | Checked on the real page, not only the code. Heights made for you (`rendered.auto`) are only the ones Figma fixes, never a component that hugs its content |
| 25 | What this audit actually checked | So you can see that nothing slipped through |

Accessibility is checked beside the gates. Part of it reads the code directly, and part of it tries the components in a real browser: on a page you name, your style guide, or your built pages, and for React components with no page to open (a project building from Figma, say), on the components themselves, rendered from their own code in each Figma variant, no dev server needed. Each component is held to its role from your Figma annotations: what it must expose (a toggle button's pressed state, a field's label, a stepper's value and range), what each part annotated in Figma owes (a label that names its field, an error message linked while it shows, a silent icon, a step button with a name), and what a person can do with it (Space flips a toggle, a click opens a disclosure, ArrowUp steps a stepper). Focus is read the way a keyboard user sees it. While a component is being built, each of these lines is part of building it. An exception is your team's decision, with a link to where it was decided. An icon that carries meaning is held to 3:1 against its background in every colour mode, so one drawn for the light theme is caught when it disappears in the dark one, and a sprite icon painted in a fixed colour of its own is caught in the code. A control said only in a tooltip (an icon whose only name is its title) is reported, since no one on a touch screen or a keyboard sees the tooltip. A state shown only by its look (selected, open, in error) is reported until a screen reader hears it too, in the words that state takes (the step a person is on is `aria-current`, an error on a field `aria-invalid`, an error on a message an announcement such as `role="alert"`), also when the look is drawn on the component and the state belongs on a part (a field disabled inside its wrapper, said in the contract's `heardOn`), and listing your system's own scripts lets the style guide run its components as your product does. Text is measured as it is drawn: see-through text blended over its background, colours written in `oklch()` or `color(srgb …)` (Tailwind v4's default) read rather than skipped (a colour space it cannot read is said, never passed), a placeholder on show measured like any text, and text inside a disabled control left alone, as WCAG allows. A focus ring kept transparent until focus counts as a focus style, a ring drawn on `::before` or `::after` is measured, and a two-tone ring passes when one of its tones stands out. A field named only by its placeholder is reported (the placeholder goes once typing starts), a role written without the state it requires (a `role="slider"` with no `aria-valuenow`, a `role="combobox"` with no `aria-expanded`) or an ARIA value the attribute does not take (`aria-live="loud"`) is reported, publishing and graphics roles (`doc-chapter`, `graphics-symbol`) are valid, and a spinner turning fast inside `role="progressbar"` is not a flash. A control's edge is held to 3:1 in every colour mode, so one that fades only into the dark background is found, with the modes it fades in.

Each finding names the component it is in, and the style guide shows each component's own findings from the last check. On the style guide a component's role is read where the component is drawn, in its own section, never on the page's own navigation that shares the system's classes, and a component the code has no markup for is said not checked rather than read on the stand-in the page draws. An option a group reaches by its arrow keys (a radio group or a tab list with one Tab stop) counts as reachable by keyboard, and a role Figma calls presentation is met by none or by a plain element. A big page (a style guide with every component drawn) is read in parts, so it is checked as fully as a small one, and a component whose selector is not valid CSS is said not checked, never clean, while the rest of the page is still checked. A state drawn with a class is heard the way the element's role says it: a selected radio is `aria-checked`, a selected toggle `aria-pressed`, a selected step `aria-current`, a selected tab `aria-selected`. Content that appears on hover or focus owes a way to close it with Escape only when it covers or replaces something; a row's action button that appears in the room the row makes for it does not. The style guide's own switches (its modes, widths and props) each say what they choose.

What the design itself owes is listed for whoever keeps the Figma file: an interactive component with no focus state (so the code invents the focus ring), an error state with no message (an error shown by colour alone), a control under 24px. Meanwhile Claude writes a visible focus ring and leaves an error message's words to you.

## Good to know

- **Which TypeScript reads your components.** Your project's own, else one installed for the whole machine (a global npm folder, `NODE_PATH`, `tsc` on the PATH). Set `DESIGN_SYSTEM_ENGINE_TYPESCRIPT=project` to use only the project's own, so a run depends on the project alone; the engine's tests do this where they expect none.

- **Share the results with your team.** Commit the files it creates in your project, so everyone, and your automated builds, check against the same design.
- **Figma stays as it is.** It only reads Figma. It tells you what to change there, and a person makes that change.
- **Reading Figma, the best way available.** `rms-design-system-engine --refresh-figma` picks it for you: a `design.json` newer than the saved data, then [figma-cli](https://github.com/silships/figma-cli) when Figma Desktop is connected to it (no API key, no rate limit, every mode), then the Figma tool of your Claude session, then the Figma API with a token. After you run `figma-cli snapshot`, the next check reads its `design.json` on its own; `--from-figma-cli` reads one directly.
- **More detail.** Everything for developers, every option and how each check works, is in [docs/details.md](details.md).
