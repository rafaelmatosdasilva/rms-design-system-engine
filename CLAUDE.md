# Working on this repository

- Update the documentation before every push: `README.md`, and any other doc the change touches, so what is pushed always matches what the skill does.
- The guide set the agent reads (`rms-design-system-engine.md`, `cookbook/*.md`, `reference/*.md`) is measured by the skill evaluation. A change to any of those files needs a fresh evaluation run and its results in `test/skill-evals/RESULTS.md` (`reference/maintainers.md`, Skill evaluation); `test/skill-evals.test.mjs` fails until then. `README.md` is outside that set.
- Before every push, run the full suite with Chrome (`node --test test/*.test.mjs`, `CHROME_PATH` set when Chrome is not on the PATH) and `node lib/sync-docs.mjs --check`; every browser test must run, none skipped for want of Chrome. That run is the gate: merge once it passes, without waiting for GitHub. GitHub runs the same suite on every pull request as a second check; a failure there is fixed like any other.
- What a measured run teaches is written down as it is learned, in `test/skill-evals/FINDINGS.md`: the case, the evidence it rests on, the guesses it ruled out, and what changed because of it. `RESULTS.md` records what a run scored; this records what reading it taught. A guess that turned out wrong is kept with its evidence, so the next person to have the same idea is saved the trip. Each study in `docs/studies/` is assembled from these, never from memory.
- When a change alters how the skill is described (README intro, what it checks, how it runs), propose new text for the GitHub About description (at most 350 characters) with the push. The owner pastes it; it cannot be set from a session.
- `README.md` is the owner's own text: the promise, Features, a line on the live style guide, Get started, Who it's for and Explore, with no diagram. Explore is one word an entry, at the owner's request: Features, Docs, Security, Studies, Governance. Change its wording only when the owner asks. Its Features list is the features page's overview, word for word: the same groups, names, descriptions and stages, its links pointing at that page. Change the two together; `test/features-page.test.mjs` fails otherwise. The flow chart and the walk through one request moved from the README into How it works in `docs/README.md` (the technical documentation's index) at the owner's request, and the detailed flow is the owner's FigJam board, linked there: https://www.figma.com/board/W5UEjkrLv5t4fqsGPQWqk8/rms-design-system-engine-flow?node-id=0-1. The owner updates the board as the engine evolves; never edit it, and add no other chart unless the owner asks.
- `docs/features.md` and the technical documentation (`docs/README.md` and one page per group) are written for people to read: headings that give a hierarchy, an "On this page" list, short sentences in plain, friendly English, and bullets or a small table where a paragraph would run long. One idea per bullet. A new feature goes into its section that way, never as one long paragraph; the full list of options stays in `reference/`, which these pages link to.
- Each part's stage on `docs/features.md` is the owner's to set, by hand, and nothing derives it. It says what is being promised to the people using the skill, not what happens to be built: a part may be held at Coming soon while its requests and its technical section already exist, and the owner may move a part up or down at any time without a line of code changing. Never compute a stage, never change one to match what was shipped, and never ask the backlog what a stage should be: propose the change and let the owner decide.
- The features page lists its parts in groups, one table each (Audit, Documentation, Collaboration, Creation), by stage inside each group, ready first; the order of the groups, and of the parts inside one stage, is the order in which they build on each other. Each part's name says what it does and what it acts on, never starts with its group's word and uses a verb no other part uses. Each description is one short sentence with the specifics (what it reads, finds or produces), the industry's own terms where they apply (contracts, intent layer, parity), and no colon.
- The technical documentation is one page per group of the features page: `docs/setup.md`, `docs/audit.md`, `docs/accessibility.md` (Test accessibility, the largest part, on a page of its own), `docs/documentation.md`, `docs/collaboration.md`, `docs/creation.md` and `docs/security.md`, with `docs/README.md` as its index and How it works. Each part a reader can use has a technical section under its own name, on its group's page. `test/features-page.test.mjs` fails otherwise. Nothing about a stage decides whether a part is documented.
- The features page is the one list of what to ask in Claude Code, at the owner's request: a **What to ask** table under each part, and a Set up section, each row the full request and what you get. Terminal-only commands are left off it (the owner's choice). No other page repeats these requests; the technical documentation and the README link to the features page. There is no separate roadmap either: the features page's Coming soon parts are it, and the project's own next steps are in `docs/governance.md`. `test/commands-page.test.mjs` fails when a request on it would only reach the catch-all full check, another page lists requests, or a link misses a heading.
- A new module goes in `lib/` and its test imports it as `../lib/<name>.mjs`. The root keeps only the four entries people's setups name (`audit.mjs`, `guard.mjs`, `mcp.mjs`, `styleguide-files.mjs`), each a one-line import from `lib/`; `test/layout.test.mjs` fails otherwise. Besides them the root holds only what something outside the repository finds there by its path (`README.md`, `LICENSE`, `package.json`, the ignore files, this file, `install.sh`, `rms-design-system-engine.md`); a page for people goes in `docs/`, and GitHub's community files (code of conduct, contributing, security policy) in `.github/`. A module reads the engine's own folder (guide, cookbook, templates, git) one level up from `lib/`.
- This repository is public: nothing private is ever committed, pushed or approved here, in a file, a test, an example, a record or a commit message. No client (its name, apps, hosts, Figma keys, component or token names), no person's name (no author credited as a source, no invented reviewer: write a role such as "QA"), no personal email (placeholders such as `example.com` and no-reply addresses only), no local path with a real folder or user name, and nothing of the backlog. Credit an idea generically ("a published article"). Examples use invented, generic names only (Acme, cardTile), never one taken from a project, even one that reads as generic. `.githooks/private-check.mjs` refuses it on every commit and every push (`git config core.hooksPath .githooks`, once per clone), with the names of every project the engine ran on, kept on this computer only (`.githooks/private-terms.mjs`); `test/no-testbed-names.test.mjs` on every test run; and the required `Privacy` check on GitHub. Never bypass them (`--no-verify`). A new private name goes into the hashed list as a hash only. Every pull request is opened through `node .githooks/private-check.mjs --pr`: it lists the names the change adds, and `--names-read` is passed only once each one has been read and none is a person or a company. See Nothing private, ever in `reference/maintainers.md`.
- Fix with the project's own code, never with a workaround invented for the occasion. When something does not work, find where the project already does that same thing and follow it: a deferral, a flag or a guard written to get past the problem is a guess, and the pattern already in the code is the answer. The same holds for what a component takes: read the component, not the name.
- The engine never changes code people wrote. Not the product's code, not the design system's, not a prototype's: what it finds there is handed back as a patch for a person to apply and shown as the difference on that component's page in the style guide. At most it writes the intent layer; everything else it flags. No setting ever says otherwise - a setting with one possible answer is a lie, and one that exists invites somebody to turn it on. The files it does write are its own (the authored contract, the structure contract's notes, the kept differences) and what it generated before (the tokens, the contracts, the style guide), each answered per place in `writes` (`writes.mjs`).
- The backlog is private and lives outside this repository. It is never named, linked, quoted or copied here: no repository or file name, no item text, no item codes. Read and change it only where it lives, and say what changed.
- Start from what is on GitHub, never from what the clone was left on: at the start of every session, before reading or changing anything, `git fetch origin` and cut the working branch from `origin/main`. The clone is one of several on this computer, each parked on its own branch, and merges happen on GitHub, so whatever is checked out is behind within a day - a session that trusts it reports a thing as absent that main has had for a week, or writes a fix on top of work already merged. A branch already checked out with work of its own is said so before anything else, with how far behind `origin/main` it is; the fix for a stale clone is a fresh branch from `origin/main`, never a change pushed from the old one.
- Leave no branch behind: with that fetch, delete every local branch whose pull request GitHub says is merged, and prune the worktrees whose folder is gone (`git worktree prune`), without being asked. Pull requests here are squash-merged, so a merged branch is never an ancestor of `main` and `git branch -d` refuses it: what says a branch is done is its pull request's state (`gh pr list --head <branch> --state all`), never ancestry, and `-D` is right once that says MERGED. Never delete the branch checked out in a worktree, one with no pull request, or one whose pull request is open: a branch carrying work nobody merged is the one thing this clean-up must not take. Say which branches went and which were kept, and why each was kept.
- Move the installed engine on after every merge: once a session merges a pull request on this computer, it fast-forwards the engine installed for Claude Code (`~/.claude/skills/rms-design-system-engine`) to `main` at once (`git pull --ff-only origin main` there), only when that checkout is on `main` with nothing uncommitted, and says so. Its own update runs once a day, so a merge otherwise reaches the person's pages a day later; moved on, the engine finds each page it builds behind, and the next Claude Code turn in that project builds it again (`git-rebuild.mjs`). It also starts the build of the public example style guide at once (its repository's `style-guide.yml`, by `gh workflow run`; the exact command is in this computer's memory, never here): that repository's own ten-minute schedule runs hours late, and no message reaches it from here while `STYLE_GUIDE_DISPATCH` is unset, so a merge otherwise left the example behind for hours.
- Read the backlog first, always: at the start of every session, and before suggesting, planning or starting any work on the engine. An idea that is not in it is said to be new, never offered as if it were planned.
- The backlog holds only issues of the engine itself: how it connects, reads and resolves content, measures, compares and analyzes. Each item is written in general terms and never names or describes a product (a plugin, an app) or a particular design system. A gap in a product or in a design system is not a backlog item: fix it there, or tell the owner.
- When the owner asks what is next to fix (accessibility or any other area), answer with the engine's own work, from the backlog: never the design system's or a product's tasks.
- A rule the owner states for how to work goes into memory at once, in the same push: this file for the engine, the backlog's own rules for the backlog.
- Releases are the week's record, and the owner never acts on them. `.github/workflows/release.yml` runs every Monday: when `main` has commits since the last version tag, it tags the next version and publishes a GitHub Release with generated notes listing the week's pull requests. People do not wait for it: every install follows `main` once a day (`lib/self-update.mjs`), so a merged change reaches them the next day whatever the release. Claude starts the workflow by hand (workflow_dispatch) only for a security fix or a fix for a problem that stops people from using the engine, and says which version went out. Nothing else is released by hand: not a new capability, not a `release: major` change, not docs. Those wait for Monday, and the week's labels set the step.

  Every pull request gets one release label when it is opened, chosen by Claude: `release: major` when something works differently for people already using the engine, `release: minor` for a new capability, `release: patch` for a fix, docs or internal work only. The biggest label among the merged pull requests sets the step (`release-version.mjs`); a pull request with none counts as minor. Only tags are written; `package.json` keeps the first version.
