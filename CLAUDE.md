# Working on this repository

- Update the documentation before every push: `README.md`, and any other doc the change touches, so what is pushed always matches what the skill does.
- The guide set the agent reads (`rms-design-system-engine.md`, `cookbook/*.md`, `reference/*.md`) is measured by the skill evaluation. A change to any of those files needs a fresh evaluation run and its results in `test/skill-evals/RESULTS.md` (`reference/maintainers.md`, Skill evaluation); `test/skill-evals.test.mjs` fails until then. `README.md` is outside that set.
- Run `node --test test/*.test.mjs` and `node sync-docs.mjs --check` before pushing.
- When a change alters how the skill is described (README intro, what it checks, how it runs), propose new text for the GitHub About description (at most 350 characters) with the push. The owner pastes it; it cannot be set from a session.
- The flow diagram in `README.md` (How it works) is built from the owner's FigJam board, its source of truth: https://www.figma.com/board/W5UEjkrLv5t4fqsGPQWqk8/Figma-to-Code-Parity---Flow?node-id=0-1. The owner updates the board as the engine evolves. Before any change to the diagram, and whenever the README is updated, read the board (Figma MCP `get_figjam` or `get_screenshot`, read only; never edit the board) and rebuild the Mermaid from it: the same phases, boxes and arrows, titles only in bold capitals (Parity output and Advisories share one box, Verdict + Advisories), no descriptions, arrow labels or emojis, so it stays readable on GitHub. The board holds the detail and is linked above the diagram. Correct only a typo or what the engine contradicts (a file's old name, a flag that does not exist), and tell the owner.
