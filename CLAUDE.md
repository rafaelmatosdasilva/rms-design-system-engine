# Working on this repository

- Update the documentation before every push: `README.md`, and any other doc the change touches, so what is pushed always matches what the skill does.
- The guide set the agent reads (`rms-design-system-engine.md`, `cookbook/*.md`, `reference/*.md`) is measured by the skill evaluation. A change to any of those files needs a fresh evaluation run and its results in `test/skill-evals/RESULTS.md` (`reference/maintainers.md`, Skill evaluation); `test/skill-evals.test.mjs` fails until then. `README.md` is outside that set.
- Before every push, run the full suite with Chrome (`node --test test/*.test.mjs`, `CHROME_PATH` set when Chrome is not on the PATH) and `node sync-docs.mjs --check`; every browser test must run, none skipped for want of Chrome. That run is the gate: merge once it passes, without waiting for GitHub. GitHub runs the same suite on every pull request as a second check; a failure there is fixed like any other.
- When a change alters how the skill is described (README intro, what it checks, how it runs), propose new text for the GitHub About description (at most 350 characters) with the push. The owner pastes it; it cannot be set from a session.
- `README.md` is the owner's own text (the promise, the three pillars, Why it matters, Get started with the most used commands, Explore and Open source), with no diagram. Change its wording only when the owner asks. The detailed flow is the owner's FigJam board, linked from How it works in `docs/details.md`: https://www.figma.com/board/W5UEjkrLv5t4fqsGPQWqk8/rms-design-system-engine-flow?node-id=0-1. The owner updates the board as the engine evolves; never edit it, and add no chart back unless the owner asks.
- `docs/features.md` and `docs/details.md` are written for people to read: headings that give a hierarchy, an "On this page" list, short sentences in plain, friendly English, and bullets or a small table where a paragraph would run long. One idea per bullet. A new feature goes into its section that way, never as one long paragraph; the full list of options stays in `reference/`, which these pages link to.
- `docs/commands.md` is the one list of what to ask in Claude Code: simple tables grouped by type (Set up, Parity, Accessibility, Ask the system, Style guide, Prototypes and building, Tokens and changes, Update Figma), each row the full request and what you get. Terminal-only commands are left off it (the owner's choice). No other page repeats these requests: `docs/features.md`, `docs/details.md` and the README link to it. `test/commands-page.test.mjs` fails when a request on it would only reach the catch-all full check, another page lists requests, or a link misses a heading.
- This repository is public: nothing private is ever committed, pushed or approved here, in a file, a test, an example, a record or a commit message. No client (its name, apps, hosts, Figma keys, component or token names), no person's name (no author credited as a source, no invented reviewer: write a role such as "QA"), no personal email (placeholders such as `example.com` and no-reply addresses only), no local path with a real folder or user name, and nothing of the backlog. Credit an idea generically ("a published article"). `.githooks/private-check.mjs` refuses it on every commit (`git config core.hooksPath .githooks`, once per clone) and `test/no-testbed-names.test.mjs` on every test run; never bypass them (`--no-verify`). A new private name goes into its list as a hash only.
- The backlog is private and lives outside this repository. It is never named, linked, quoted or copied here: no repository or file name, no item text, no item codes. Read and change it only where it lives, and say what changed.
- The backlog holds only issues of the engine itself: how it connects, reads and resolves content, measures, compares and analyzes. Each item is written in general terms and never names or describes a product (a plugin, an app) or a particular design system. A gap in a product or in a design system is not a backlog item: fix it there, or tell the owner.
- When the owner asks what is next to fix (accessibility or any other area), answer with the engine's own work, from the backlog: never the design system's or a product's tasks.
- A rule the owner states for how to work goes into memory at once, in the same push: this file for the engine, the backlog's own rules for the backlog.
